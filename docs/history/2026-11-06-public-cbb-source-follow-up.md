# Public CBB witness follow-up

The official [CBB copy example](https://prodocs.easyeda.com/en/api/reference/pro-api.lib_cbb.copy.html)
obtains a candidate through a system-library search. It publishes no fixed CBB
UUID or anonymous HTTP response that can serve as the required positive
system-owned fixture. It is an SDK usage example, not evidence that a particular
candidate is currently accessible through the installed209 profile. No copy or
library write was executed.

I inspected the vendor's
[reuse-block extension at c24c7228](https://github.com/easyeda/eext-ai-reuse-block-placement/tree/c24c7228b022c53e509788ef375e1bf81bd82966).
Its [catalog implementation](https://github.com/easyeda/eext-ai-reuse-block-placement/blob/c24c7228b022c53e509788ef375e1bf81bd82966/src/catalog.ts)
resolves available library collections, pages their SDK search results and
obtains detail separately. It supplies no fixed positive system CBB witness.
Its comments report search/detail classification differences on V4.1.71;
those comments do not qualify installed209 behavior. Its fallback that returns
null on detail failure cannot establish absence or complete membership for
this plugin. The repository was read in private temporary storage; its code
and scripts were not executed or copied into the package.

The public SDK inventory and historical HTTP403/empty results remain separate
from positive response validation. No earlier absence probe was replayed and
no source example was relabelled as a connected test. The remaining concrete
dependency is a currently accessible anonymous system-owned CBB whose project,
branch and reciprocal board structure pass the maintained getter. This record
adds source evidence, not a claim that no public CBB exists.
