# Standalone circular Pad point reader

This source increment adds the separate `observe-spatial-pads` alternative to
the original `pcb-spatial209` lifecycle. It accepts one to sixteen ordered point
queries and consumes the same once-only observation slot as Via, Line/Via and
Arc/Line/Via. Its result, observation, intent and retained result use distinct
`pcb209-spatial-pad-point-*.v1` schemas. Earlier schemas remain unchanged.

The full indexed scene must consist of ready standalone standard `Mi` views and
`tE` models on copper1 or2. The selected native style is a circular `tC` ELLIPSE.
The original model/view cached bounding box must equal center plus/minus radius.
Rotation, parent, smart Pad, test/marker Pad, refresh, hover, pending index and
other families refuse before native hit methods. The result preserves the
original point winner and selected-ID order across two samples. Region queries
are rejected by the public schema, pipe codec and fixed native program.

The source roster has215 original callables. It removes31 unreachable Via and
region callees from the226-callable base and adds20 Pad classes, methods and
accessors, including the actual `tC.inShape` method independently. The unchanged
384-request purpose needs103 opening/source/reproof requests,7 capture requests,
one function array, one tuple,215 callee metadata requests,16 point queries and
one original group release. Total344 leaves40 requests of headroom. The retained
original parent, script, context, function, descriptor and index checks still
apply. No arbitrary code or caller limits are accepted.

The maintained offline checker
`plugins/easyeda-pro-control/scripts/check-current-pcb209-spatial-pad-source.ts`
verifies the complete pinned10,991,441-byte PCB source SHA
`a84059304d32d4f0feb768d6c5baf00d72a954643ac62299f2c46c08fa68fd0b`,
every215 source span, and seven actual circular point cases through the pinned
`Mi.isSelect`, `tE.inShape`, `tC.inShape`, `j1` and numeric vector methods.
It allocates no app/native owner. Synthetic regressions separately cover guard
ordering, second-sample drift, finite pipe sequencing and original lifecycle
journaling. These are source and offline results; connected acceptance is false.

Component point selection remains refused. `Hr.pointSelectBeforeFilter` passes
the third argument `true` to `Le.isSelect`. That path uses `Ji`'s actual footprint
layer-box cache, `gqe`/`yqe`, the `Ae` matrix graph and transformed `iE` setters
that write the static `iE._modify` flag. The ordinary model bounding box alone
does not qualify that path. Component region selection also needs `Gs` and the
cache lineage. No null-cache or axis-aligned shortcut is used.

The current Via/Line/Arc generated archives contain no Pad, so they cannot prove
a positive Pad case. The next fixture increment must provide a separately
qualified standalone circular SMT PAD archive and full initial SQL target,
then root must run the maintained import/closure/staging/spatial lifecycle.
No Component or Pad connected result is claimed here.

Integration requires regenerating the spatial native marker using the maintained
generator, updating only root-owned helper/payload pins, and exposing the updated
existing `pcb209-spatial` request schema. No new index owner or lifecycle purpose
is needed. `observeSpatialPad209` is retained and pinned beside the existing
three original spatial methods by the lifecycle itself.

Validation used pinned Node24.18.0. The three new kernel tests, production pipe
Pad test, original lifecycle Pad test and corrected original-inspector regression
passed. Both TypeScript projects and strict type-aware lint passed. A temporary
copy of the maintained generated helper compiled under Linux .NET10 and its
actual `VerifySpatial209Smoke` passed, including Pad variant isolation, sixteen
reads, region rejection and original release. The tracked helper and pins were
not regenerated by this child. Windows compilation and connected Pad validation
remain root-owned prerequisites.
