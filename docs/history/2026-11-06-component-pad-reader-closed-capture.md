# Component closed capture and Pad report-chain correction

The Component reader now offers its separate
`capture-component-generated-closed` action under the original
`component-spatial` wrapper. It requires the original operation/binding digest,
`confirmReadClosedFixture:true`, the same genuine Component source and prepared
checkpoint, actual retained root/empty-Job termination and an unreleased helper.
It consumes one capture attempt, journals its own intent/result filenames, and
reproves the original owner/closure around the data work. Caller paths,
qualification JSON and another purpose cannot supply these inputs.

The provider `captureGeneratedComponentReaderClosedSnapshot` preserves the
Component/FOOTPRINT brand and its exact prepared qualification. It shares only
new no-follow Linux descriptors, directory/file identity and roster reproof,
complete byte copy/rehash, SQL inventory and raw-history decoding with the older
reader. Its own `generated-component-reader-closed-snapshot.v1` report includes
the original preparation-checkpoint hash. No old PCB alias or parser is widened.
The shared mechanism issues no project target or runtime authority. Existing PCB
and standalone Pad report schemas and explanatory fields remain unchanged.

Current initial qualification uses the newly observed file birth/mtime values.
Zero DrvFS birth time remains a qualification refusal: it does not borrow the
positive clocks of the earlier import qualification. Complete closed bytes,
all 35 SQL tables and raw history can still be captured and compared independently.
Clock refusal grants no writer, startup-effect acceptance or new opening token.
Component report/intents/results have separate schema literals and filenames.

The frozen Pad case exposed an actual provider/scanner mismatch: the provider
emitted `generated-pad-reader-closed-snapshot.v1`, while the scanner accepted
only the generic report. This source correction recognizes the maintained Pad
report only for its exact generated Pad filename/path, project and original
qualification hash. New Pad captures also journal their complete original Pad
qualification and bind its target, archive and hash. The old generic intent
shape remains readable for the earlier frozen Pad record. Cross-schema Pad/PCB
reports refuse. No historical record is edited or relabeled as released.

Closed-report candidate chains are now checked before result retention or
publication. A wrong report cannot first become an invalid journal record and
strand its original helper. The capture remains consumed, its valid intent stays
preserved, and original termination/release still works. This does not relax the
shared scanner or bypass original-owner cleanup.

Eight isolated focused checks pass: existing Arc/full-byte/SQL/raw-history
capture and descriptor/callback guards; actual Pad schema plus legacy intent
acceptance and helper release; cross-schema refusal before publication with
cleanup still available; the separate Component action/checkpoint/report chain;
and real Component bytes/all35tables/raw footprint/Pad/attribute source with fresh
clock forwarding and explicit zero-clock refusal. Lifecycle owners and the
Component preparation boundary are explicit synthetic seams; no Windows/CAD
validation is claimed. Full strict types and changed-file type-aware lint pass.
No application, Windows process, MCP call, file restore, Save, deletion or native
helper regeneration ran. The already-loaded frozen Pad process cannot load this
fix; its exceptional cleanup and separate historical relinquishment are owned
by the integration task.
