# Generated fixture handoff in the registered tools

The registered fixture tool now exposes `stage-for-fresh-opening` after complete
original cleanup, `capture-closed-import`, destination release and owner
release. It requires the original base import ID and
`confirmStageClosedFixture:true`. The original coordinator rechecks its runtime
and methods, issued complete closed qualification, retained archive and drained
library-migration exclusion. The action starts no application and transfers no
native owner, process handle, Job or HMAC session.

An independent private index slot retains the opaque generated-data token
through ordinary helper release. Only the next ordinary or spatial reader
construction may consume it. Existing native allocations refuse before that
consumption. Construction consumes the slot before the original token reaches
the constructor; failure cannot reuse a serialized report. The spatial native
birth extension remains pending at this checkpoint. New import allocation
cannot overwrite an already-staged source.

The released import coordinator's ordinary `execute` path explicitly refuses
this local action. A regression proves it cannot fall through into destination
release or dispatch any native/SDK work. The actual registered callback is
also exercised with the production upstream authentication scope: staging
retains the exact source object, requires no live scope and refuses overwrite.
One outdated synthetic fixture initially lacked the new index variable; it was
corrected and the registered callback then passed. Original owner/runtime,
publication, generated native registration and staged-token checks pass in
the focused cases. Final combined helper/bundles, strict checks and connected
import/read acceptance are still pending.
