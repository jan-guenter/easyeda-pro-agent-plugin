## Exclusive creation and stable write parents

The current owner checks that the scratch root is absent at line 39, calls
`DirectoryInfo.Create(DirectorySecurity)` at 44, then creates ten child
directories at 47. The first receipt invokes `No-Reparse` at 48. Microsoft's
documented overload applies security during creation but returns without
creating anything when the directory already exists. The earlier absence check
therefore does not make root creation exclusive.
[DirectoryInfo.Create](https://learn.microsoft.com/en-us/dotnet/api/system.io.directoryinfo.create?view=netframework-4.8.1)

Inference from this order: a competing directory can be adopted between 39 and
44, and a substituted ancestry can affect child preparation before its later
detection. This is an unlaunched preparation race: the Job is not constructed
until line 64. Stopping a subsequently owned process cannot undo those writes.
No native reproduction or unintended write is claimed here.

`CreateDirectoryW` fails when the final directory already exists and accepts a
security descriptor. It is a candidate exclusive-create primitive, but it
returns no retained directory handle. A subsequent open can still observe a
replacement; that pair must not be described as atomic retained-root issuance.
[CreateDirectoryW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createdirectoryw)

A more direct design candidate is documented `NtCreateFile`: `FILE_CREATE`
refuses an existing object, `FILE_DIRECTORY_FILE` requests a directory, the
operation returns its handle, and `OBJECT_ATTRIBUTES.RootDirectory` permits a
single relative name beneath an already retained parent. A supplied security
descriptor applies on creation. This is a proposed narrow primitive, not a
reviewed P/Invoke implementation or a native compatibility result.
[NtCreateFile](https://learn.microsoft.com/en-us/windows/win32/api/winternl/nf-winternl-ntcreatefile)

Root creation alone is insufficient. Every parent used for later writes must
remain bound to the admitted object through those writes and the scratch
process lifetime. A reviewed implementation should retain no-delete handles for
the relevant ancestry and each newly issued directory, reject reparse objects,
and verify handle/named identity. `CreateFileW` supports directory handles with
backup semantics, opening a reparse object rather than its target, and sharing
restrictions retained until close; omitting delete sharing excludes later
delete/rename opens. Those facts do not make a sequence of path checks atomic.
[CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew)

Handle-derived volume/file identifiers can check whether a named path still
refers to the retained directory. They are identity evidence, not by themselves
a lock on every ancestor or an exclusion of in-place reparse/attribute changes.
The precise access/share policy and component-by-component path construction
need review and hostile synthetic controls before use; a `No-Reparse` check
followed by ordinary path-based child creation is not enough.
[GetFileInformationByHandle](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getfileinformationbyhandle)

### Follow-up filesystem contract

Read-only sharing is not a reparse lock. `CreateFileW` excludes attribute access
from its sharing restrictions, while the published filesystem algorithm permits
reparse mutation with `FILE_WRITE_ATTRIBUTES`. The design must therefore test
an existing attribute handle changing a parent in place, not only attempts to
rename a directory. No such native test has run.
[CreateFileW sharing rules](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew),
[FSCTL_SET_REPARSE_POINT](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-fsa/4aeefef8-92c3-4abc-af7a-a610caf8a165)

The proposed first implementation uses fixed directory/file roles and
single-component operations relative to retained parents. `FILE_CREATE` owns the
new handle immediately; a later validation failure must still clean it up.
`OBJ_DONT_REPARSE` refuses reparses encountered during name parsing. The docs do
not establish that it re-examines a previously opened `RootDirectory` changed
in place. That is an explicit qualification requirement, not an assumed lock.
[OBJECT_ATTRIBUTES](https://learn.microsoft.com/en-us/windows/win32/api/ntdef/ns-ntdef-_object_attributes)

Creating a retained guard file can make an ordinary directory nonempty, but it
does not happen atomically with directory creation. A failed guard insertion
leaves partial preparation that must not be reused. Similarly, closing a writer
and acquiring a verified read lock is a checked transition, not uninterrupted
write exclusion. The first filesystem implementation should report preparation
and cleanup only. It must not issue permission to launch Electron by pathname;
that later handoff needs separate reparse, sharing and runtime qualification.

The [retained-parent research](2026-10-12-native-relative-parent-reparse.md)
separates the documented guarantees from the unresolved transition through an
already-open parent. It defines the next synthetic controls for conversion
before and after guard insertion. No native result is inferred from that research.

## Owned process cleanup and observed exit

The C# owner retains the original process and Job handles and start time. It
sets only kill-on-close limits and supplies the Job in process creation, with
no existing-process attach path. The PowerShell success path at lines 77–78
requires root exit, a complete empty Job list, exit zero and no failure receipt.
These protections must remain when preparation is hardened.

On failure, `owner-command.ps1:83` requests termination of its own Job, then
queries it for up to five seconds. Job termination applies to associated
processes, while process termination initiated externally is asynchronous;
requesting it does not establish observed exit. Keep the original handles long
enough to observe the result and retain uncertainty when that fails.
[TerminateJobObject](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-terminatejobobject),
[TerminateProcess](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-terminateprocess)

The cleanup order matters. Closing the final kill-on-close Job handle is a
containment mechanism, not a later observation that its membership is empty.
Closing a process handle does not terminate that process. Preserve process/Job
observations before disposing their evidence-bearing handles; never close a
handle while a wait on it remains pending. A failure-path fallback may close
the Job for containment, but must not relabel the unobserved remainder as
proved cleanup.
[Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects),
[CloseHandle](https://learn.microsoft.com/en-us/windows/win32/api/handleapi/nf-handleapi-closehandle),
[WaitForSingleObject](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-waitforsingleobject)

Current line 86 disposes the Job, then each file lock sequentially; a thrown
Dispose can skip subsequent handles. `OwnedSyntheticJob.cs:91` ignores both
`CloseHandle` return values. The narrow remedy is attempt-all cleanup with the
primary error and all cleanup errors retained. Keep root/parent and input locks
until owned process work has ended or cleanup is explicitly unresolved; do not
publish success after required cleanup fails. This is a source finding, not
evidence of an escaped native process.
