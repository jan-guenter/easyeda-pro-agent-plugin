# Original-process cleanup after ordinary tracked opening

This source-only follow-up adds reachable cleanup to the Nov 5 schematic-page
opener. The same internal owner is shared with the separately implemented managed
fixture importer. It does not open an application, contact a live CAD bridge,
open a production project, edit a design, dispatch Save or publish/install the plugin.

The cleanup constructor receives the actual original ordinary
`WindowsControlRuntime` and an index allocation guard. It retains only the actual
new managed operation object immediately before its tracked dispatcher. The
engine now records settlement of that exact dispatch Promise and retains the
original immutable plan, authority capture, authenticated session, dispatch
binding, runtime identity and validator method identities. A copied or loaded
journal, replacement runtime, changed plan or still-pending dispatcher cannot
supply cleanup authority. The engine-issued technical nonce is useful only with
that original retained owner. Its explicit internal phase allowlist is
`schematic-page-open209` and `managed-fixture-import`; existing generic recovery,
writer and diagnostic guards are unchanged.

The registered schematic wrapper offers `request-cleanup-close`,
`observe-cleanup-termination`, `finish-cleanup` and `settle-cleanup-records`.
These actions serialize on the original bridge gate outside an authenticated
dispatch scope. The close request needs explicit original-normal-close and
unknown-file-effect acknowledgments. It publishes intent before one fixed
normal close to the observed original HWND, rechecks that same HWND before
dispatch and consumes the native stage before awaiting acknowledgment. Neither
native close uncertainty nor local publication failure can repeat it. No prompt
choice, discard or force termination is provided. Normal closure may persist
application data.

Termination uses retained original root and Job handles, requiring root exit and
a complete empty Job. Finish separately reobserves termination and calls the
existing upstream closed-dispatch assertion. That assertion verifies the exact
old session and HMAC dispatch receipt, requires no current authenticated context
or lease, and never releases a lease itself. Original process closure is not a
saved-content proof. Only after these checks does the owner consume its technical
nonce and publish a terminal quarantine clear. The record says navigation and
storage effects are **unknown**, preserves `mutationMayHaveOccurred:true`,
`saved:false` and `reopened:false`, and grants no replay or writer authority.
Capture release follows durable quarantine clearing. An ambiguous release is
consumed once; final original helper release remains with the ordinary launch
owner after its termination record.

Local publication has its own retained settlement. Pending artifact content,
base journal and candidate journal remain exact in memory. Settlement accepts
only the same verified old journal or this owner's exact candidate and exact
artifact bytes; foreign content refuses without overwrite. A lost terminal
publication acknowledgment can settle after technical nonce consumption using
the original pending candidate, allocation/validator/source identity reproof,
fresh original termination and exact closed-session/lease reproof. No historical
JSON can reconstruct this capability. If a consumed close request has not yet
reached native dispatch, its original confirmations can proceed to the first
close after durable intent and a fresh same-window observation. Settlement never
repeats an already dispatched native close, navigation, import or Save.

The original ordinary launch's supported `observe-termination` and
`release-closed` remain the final launch-record/helper steps after quarantine is
cleared. Cleanup does not clear allocation globals, adopt a new owner, restore a
file or claim effects were absent. Loss of the original facade's private object
and native handle custody remains outside this source-only capability.
