# Historical closed generated-reader relinquishment

Use this route only for the reviewed frozen4500 circular Pad reader whose
closed capture published a distinct Pad report before its older journal reader
rejected that schema. Its original application root and empty Job were recorded
closed. The original helper release was not acknowledged.

This route does not close the retained original facade or helper. Finish their
separately authorized cleanup and independently observe their original exits
first. A new facade cannot adopt those process handles. Keep the original
journal and every failure unchanged.

1. Select and admit a verified new facade with no previous application-owner
   allocation. Source/reference queries are permitted. Do not stage a fixture,
   launch EasyEDA or reserve another native workflow in that facade first.
2. Query offline `{action:"closed-reader-relinquishment",query:{includeSchemas:true}}`
   through `easyeda_control_api`. Validate through
   `{action:"closed-reader-relinquishment-validate",query:{request:...}}`.
   `includeSchemas` belongs inside `query`. A top-level field is rejected before
   any historical qualification or native request.
3. Send the validated request directly under `easyeda_control_pcb209_opening`.
   Use `action:"relinquish-closed-reader"`, the original operation ID, the exact
   reviewed roster digest, `confirmRelinquishClosedReader:true` and
   `acceptMissingHelperReleaseAcknowledgment:true`. The schema accepts no PID,
   path, caller observation, nonce, replacement target or release-success flag.
4. The coordinator checks all21 original records by descriptor, exact raw-byte
   digest, complete roster and maintained chain validation. It verifies the
   retained complete raw project, SQL and raw-history artifacts. It then makes
   two native Windows absence samples and two independent Linux facade checks.
   Any EasyEDA, other PowerShell or other facade presence refuses. Absence does
   not prove native handle release or recreate original custody.
5. Successful completion appends a separate intent and relinquishment receipt.
   It removes only this exact historical startup blocker. All native release,
   adoption, writing, Save and persistence flags remain false. Normal future
   native workflows still require their own new owner and complete admission.

Only the complete frozen4500 Pad failure is recognized. Other incomplete
journals remain blocked. A modified original record, new file, changed artifact,
partial or contradictory receipt refuses. An opaque historical token copied
through JSON cannot select a global exclusion.

After an uncertain publication, inspect the retained original result and use
the same coordinator to settle its pending metadata. The repeated request can
return an existing matching receipt or finish the original pending publication;
it cannot repeat a native close, release, query, navigation or Save. A pending
metadata publication continues to reserve that facade. Do not modify receipts
or use another controller to bypass it.
