## Method and argument discovery

- Look up methods and exact operation arguments with offline `easyeda_control_api`; read [api-reference.md](api-reference.md). Its latest SDK snapshot is documentation, not execution authority. Validate assembled operations offline before a live preflight.
- Use its `coverage` action to distinguish direct SDK calls, narrower native task equivalents, lifecycle-only calls and omissions. `easyeda_control_sdk_read` exposes fixed typed local getters and calculations. Matching samples are public SDK observations, not complete native design or persistence proof.

## Supplied files, calculations and catalogs

- For supplied-coordinate geometry, query `calculations` and validate with `calculate-validate`. The separate `easyeda_control_calculate` accepts sixteen bounded method subsets on its reviewed new-version tuple. Clipping has stricter orthogonal integer-ring limits; see the API reference before preparing inputs. It needs an authenticated fingerprint but no active design. Restricted mode has no generic design, navigation, native UI or design-recovery tools; disposable opening has its own contract below.
- For mil/mm/inch conversions and bounded environment metadata, query `system`, validate with `system-validate`, then use `easyeda_control_system` with the actual authenticated fingerprint. Read the API reference for rounding, signed zero and version-comparison direction. These methods do not change editor units or establish project/account state.
- On the separately reviewed 3.2.209 profile, query `public-readers` and validate with `public-readers-validate` for supported languages, SDK-resolved language, API-page viewport, resolved UI theme, global toolbar units, the fixed system-library UUID or selected bottom-library row metadata. The row reader accepts only a UI-reported system-library UUID and does not prove the asset belongs to it. SDK-resolved language may be a fallback and does not prove provider success. Use `easyeda_control_public_readers` with the authenticated fingerprint; read [the utility contract](current-utility-readers.md#language-and-api-page-viewport-readers). Toolbar units do not establish document coordinate scale, and viewport dimensions do not describe the operating-system desktop or PCB geometry.
- For two supplied Allegro netlists, read [managed netlist comparison](current-netlist-files.md), discover `netlist-files` and validate with `netlist-files-validate`. `easyeda_control_netlist_files` prepares each managed input locally, then compares exact returned descriptors through the authenticated app. It compares footprint/designator and net/pin memberships only. It does not export a design or accept document UUIDs, and equality does not prove component values or circuit correctness.
- For supplied library metadata, symbol pins or project-archive sources, read [managed library files](current-library-files.md), discover `library-files` and validate with `library-files-validate`. `easyeda_control_library_files` prepares exact managed inputs, reads metadata and indexes footprint/SYMBOL or current mixed-document project sources for lossless digest-bound paging entirely offline. Separate reports inspect supported symbol pins, raw schematic records and persisted PCB stack/rules. They preserve raw source fields and record hashes without compiling connectivity or evaluating effective rule precedence. It does not invoke the SDK, import files or prove live membership, geometry, dependencies, connectivity or electrical correctness.
- For one known public system-footprint UUID, read [the catalog contract](current-system-library.md), then discover `catalog-footprint` and validate with `catalog-footprint-validate`. The separate `easyeda_control_catalog_footprint` requires `confirmNetwork:true` but no app/bridge/fingerprint. It performs a fixed credential-free vendor HTTPS lookup, not SDK execution. It returns metadata, not geometry; an unsuccessful response does not prove absence.
- For public footprint/symbol/device/3D-model/panel search, footprint/symbol lookup by name, device lookup by LCSC code or known symbol/device/panel metadata, use `easyeda_control_catalog_components` after `catalog-components`/`catalog-components-validate` discovery and [the catalog contract](current-system-library.md). Explicit network confirmation is required. Search results are candidates; device associations are not pin mappings. Model/panel geometry and downloads remain unavailable. Do not send private design data.

## Loaded-project and editor readers

- For current-version PCB layer metadata, query `pcb-layers`, validate with `pcb-layers-validate`, then use `easyeda_control_pcb_layers` with an explicit project/branch/document/tab target. Read the API reference for native-equivalent execution, raw colors and copper-count semantics. It does not select layers, open a board or certify its physical stackup.
- For current-version selected IDs or unfiltered Line/Arc/Via/Component/Pad/String/Dimension/Image/Attribute IDs, use offline `pcb-identities`/`pcb-identities-validate` then `easyeda_control_pcb_identities`. Attribute results retain observed component grouping; positive type lookup remains limited to Line/Arc/Via. Read the API reference for loaded-view membership and bounds; these IDs are not a complete saved-design inventory or editing authority.
- For one project-local symbol's metadata on the current tuple, query `project-symbol`, validate with `project-symbol-validate`, then use `easyeda_control_project_symbol` with an exact active PCB target. Read [the metadata contract](api-reference.md#current-project-local-symbol-metadata). The symbol must be absent from the tab registry. This read does not load symbol geometry, contact a cloud library or enable renaming.
- If the project is loaded without editor tabs, use the separate `project-symbol-preflight` discovery and validation request on that same tool. Read [the no-editor contract](api-reference.md#symbol-observation-with-no-editor-tabs); do not open a PCB just for this comparison. Caller-supplied expected metadata is not provenance or permission to write.
- For schematic-container or sheet metadata with the project loaded and no editor tabs, query `project-schematic`, validate with `project-schematic-validate`, then use `easyeda_control_project_schematic`. Read [the schematic metadata contract](current-schematic-readers.md). Selected sheet lookup requires both its page UUID and parent schematic UUID; collections retain complete observed parent membership. This does not read sheet contents or qualify a rename.
- For board IDs returned by project metadata, query `project-board`, validate with `project-board-validate`, then use `easyeda_control_project_board` with no editor tabs. Read [the board metadata contract](current-board-readers.md). Raw board titles/order/tickets do not establish child relationships, physical PCB contents or rename authority.
- For one PCB's metadata or the complete observed PCB metadata map with the project loaded and no editor tabs, query `project-pcb`, validate with `project-pcb-validate`, then use `easyeda_control_project_pcb`. Read [the no-editor PCB contract](current-pcb-readers.md#project-local-pcb-metadata-without-an-editor). It preserves native title/display-title distinctions without opening a canvas; it does not qualify a rename or prove saved state.
- To compare an ordinary PCB against expected metadata and observe a proposed title's availability, query `project-pcb-preflight` and validate with `project-pcb-preflight-validate` before using that same tool. Read [rename preflight](current-pcb-readers.md#read-only-rename-preflight). Complete native peer, client/ticket and UI clock observations do not authorize a rename or prove saved history.
- For current-version PCB geometry, text, Component metadata, Pad parameters, Dimension coordinates or Image placement, use offline `pcb-geometry`/`pcb-geometry-validate` then `easyeda_control_pcb_geometry`. Use `getAll` with empty arguments or `get` with distinct `primitiveIds`; explicit IDs still require complete-family validation. `getSelectedPrimitives` accepts empty arguments and returns supported geometry in current selection order, refusing any missing or unsupported selected object. `getAllPinsByPrimitiveId` accepts one component `primitiveId` and correlates its native child list with global Pad membership. Read [current PCB readers](current-pcb-readers.md) for fields, units and family-specific limits. Loaded-view geometry and parent groups do not prove saved membership, rendering, reciprocal ownership, connectivity or schematic pin mapping.
- For configured shortcut listings, query `shortcuts`, validate with `shortcuts-validate`, then use `easyeda_control_shortcuts`. Read the API reference for the optional system filter, raw key strings and shortcut-specific scope enums. The result neither presses keys nor proves that a shortcut can execute in the current focus.
- For extension startup investigation, query `extensions`, validate with `extensions-validate`, then use `easyeda_control_extensions`. It observes selected metadata from the initialized user-extension index only. Read the API reference before interpreting it; it cannot establish the database's current account, loaded code, builtin inventory or permission to launch.
- Use `easyeda_control_editor_shell` for authenticated, privacy-limited tab counts and registered Start Page flags on the current reviewed UI. It does not prove window visibility, completed restoration or project closure, and does not authorize navigation.
- Use `easyeda_control_editor_context` when only active-document and current-project/branch identity is needed on the current tuple. Read the connection reference first: unsupported tabs and missing fields are explicit, and this result cannot replace legacy transaction context or authorize a later operation.

## Scoped metadata changes

- For a title-only change in an explicitly disposable project, read [disposable PCB rename](current-pcb-rename.md). Query `disposable-pcb-rename`, validate with `disposable-pcb-rename-validate`, then use `easyeda_control_disposable_pcb_rename` from the retained disposable opening. Follow its exact phases through normal closure, full SQL effect and fresh saved metadata verification. Installed195000 passed one complete disposable lifecycle; that historical result does not admit another payload or invocation. Ordinary projects, linked reuse propagation and inverse remain excluded.
- For an ordinary project's schematic-container title, query `project-schematic-operation`, validate with `project-schematic-operation-validate`, then use `easyeda_control_project_schematic_rename`. Read [schematic rename lifecycles](current-schematic-rename.md). Installed203733 passed this route's own complete title-only lifecycle, including batching and closed/reopened/full-SQL proof, on a disposable fixture. Its sealed startup, original owners and one-write guards remain mandatory; legacy disposable confirmation at open is optional. The separate disposable route keeps its required confirmations and scope. Neither route renames sheets, edits circuits or provides an inverse. Historical evidence is not current admission.
- To prepare a symbol name/description change from an existing managed checkpoint, use offline `project-symbol-preparation`, `project-symbol-prepare-validate` and `project-symbol-prepare`. Read [checkpoint preparation](api-reference.md#checkpoint-bound-symbol-preparation) first. Supply the exact checkpoint path/bytes/hash and project/branch/owner/symbol IDs. This verifies selected-branch records and peer names without accessing the original design; it neither creates a checkpoint nor enables a writer.
- For that supported ordinary metadata change, discover `project-symbol-operation`, validate with `project-symbol-operation-validate`, then use `easyeda_control_project_symbol_metadata`. Keep its original opening/baseline owners and follow the returned phase. Its purpose is separate from disposable validation; no inverse or replacement-runtime continuation is accepted.
- To create a drawn-symbol fixture by copying an existing supported symbol, read [disposable symbol copy](current-symbol-copy.md). Discover `disposable-symbol-copy`, validate with `disposable-symbol-copy-validate`, then use `easyeda_control_disposable_symbol_copy` from the original disposable opening. It has distinct baseline/copy ownership, one native copy, exact closed SQL and saved-reopen verification. Installed094000 passed one supported disposable drawn-symbol case; that historical result does not admit a later generation. Ordinary-project copying, caller-selected names and inverse/delete remain unsupported.
- For explicitly authorized disposable symbol-metadata validation, read [forward/inverse validation](current-project-opening.md#disposable-forwardinverse-validation). The separate `validation-*` actions consume that same prepared baseline and can change its sealed symbol name/description, verify persistence, and derive an inverse. The target must be unreferenced by active schematic pages and have complete META-only history or satisfy the bounded canvas-segments profile. Installed210000 passed the latter's disposable round trip with exact SQL, reopened content and metadata restoration; linked-sheet propagation and other drawing histories remain unsupported. Installed080000 separately passed one ordinary unused drawn-symbol case. Neither historical result grants current-operation authority or validates other histories. Follow the returned exact phase; do not replay a lost response or restart midway.

## Launch, connection and cleanup

- For a stopped sixteen-event closed-symbol validation at the fixed marker-read boundary, or a completed closed baseline stopped before its relaunch intent, read [failure-recovery.md](failure-recovery.md) and use offline `history`/`history-validate` before `easyeda_control_history`. Its separate exact-prefix actions qualify local historical abandonment only, not generic recovery, restart or replay.
- For current-version disposable PCB opening, read [current-project-opening.md](current-project-opening.md), then use offline `project-open`/`project-open-validate` and `easyeda_control_project_open`. It requires an already registered disposable file, checkpoint-member PCB, initially empty editor and this facade's retained ordinary launch. Normal opening can migrate data or automatically Save. Each stage runs once; inspection and observation never replay navigation.
- For a failed disposable opening, keep the original facade alive and use its supported `request-normal-close`, then `retire-after-termination`. Read [the interrupted-call contract](current-project-opening.md#interrupted-calls) first. This original-owner cleanup leaves quarantine set until termination proof; it cannot adopt a process or answer Save/Discard.
- For disposable startup qualification, use that tool's `baseline-*` actions only after reading [the retained baseline workflow](current-project-opening.md#retained-baseline-validation). Keep the same facade alive through close, copy, relaunch and project-only reopening. These actions do not write symbol metadata or enable a writer. Finish with the baseline's own normal-close and termination actions, not the older launch receipt.
- For the current writer's exact history-date controls, read [optional clock preparation](current-project-opening.md#optional-current-clock-preparation). `baseline-prepare-clock` belongs before replacement relaunch; `baseline-observe-clock` belongs after project-only opening. Both consume one original attempt and leave writer authority false.
- After successful retirement with both snapshots captured, use offline `baseline-analysis`, `baseline-analysis-validate`, then `baseline-analyze` to compare retained files. Read [the analysis limits](current-project-opening.md#compare-retained-snapshots). Historical equality and retained clock observations do not establish backend identity, startup completion or writer authority.
- When ordinary startup is within the task, use `easyeda_control_launch` on its supported installation instead of repeatedly asking the user to start EasyEDA. Read the connection reference first. It uses the existing profile, journals one attempt and does not prove isolation, connection or Start Page readiness. Inspect uncertain attempts; never repeat them under a new ID.
- For normal closure of this facade's retained ordinary launch, use its `observe-window` and confirmed `normal-close` actions, then separately `observe-termination`. Read the connection reference first. This avoids foreground input, but never answers Save/Discard, forces exit, repeats close or bypasses quarantine. Lost original handles cannot authorize it.
- After a facade restart loses launch handles, read the connection reference before recovery. An acknowledged launch can use `abandon-supervision`; a reviewed intent-only launch can use `abandon-unknown-launch` from a fresh coordinator, before allocating a runtime. Neither proves termination or clears design quarantine. Presence observation alone does not authorize relaunch.
- For setup, missing tools or connection trouble, read [connection-and-context.md](connection-and-context.md). The bundled portable launcher loads a private machine profile. The checkout-only foreground client uses the same facade when no other owner is running.

identified disposable project. They are separate diagnostic lifecycles, not
prerequisites for ordinary design inspection. Choose the needed purpose before
launch; an existing owner cannot be upgraded.

- For footprint development needing one original main/renderer generation, read [combined validation](current-footprint-combined.md), discover `footprint-combined` and validate with `footprint-combined-validate`. It requires published main construction before disposable project capture and retains the worker/cache/actor/route guards. Its historical unknown-launch relinquishment requires a fresh facade before allocating any startup coordinator, including through `inspect`. It offers explicit original-Job abort and no copy/delete, backend request collection or Save.
- For disposable PCB camera/window work on 3.2.209, read [the visual workflow](current-pcb209-visual.md), discover `pcb209-visual` and validate with `pcb209-visual-validate`. Use `easyeda_control_pcb209_opening` with its separate `visual` wrapper and a new original visual owner. One viewport operation preserves selection. Fit-all, fit-selected and zoom-to report one native camera-bound result. Fit-board-outline reports only native `fitBoard` submission, with no bounds or verified camera effect. Coordinate/region navigation requires explicit transient-overlay acceptance and reports only a native boolean acknowledgment, with no camera, render or timer-completion proof. Up to eight `observe-capture-readiness` queries report geometry and capacity without consuming capture. A maximized visible original window can use one `restore-window-for-capture` request with explicit restore-effects acceptance, including possible position change; new same-HWND nonmaximized readiness is required before optional fixed `resize-window-for-capture` or capture. Resize requires another matching geometry/position observation. The separately consumed `capture-window` returns a bounded managed PNG and retains native resources until actual root exit and empty Job. Choose the separate `capture-renderer-viewport` action before capture when the application renderer viewport is needed. It uses fixed PNG screenshot flags on the original Page session and accepts no caller target, clip or options. Both image methods share one consumed slot, so a blank or failed capture cannot trigger a fallback. Renderer pixels include application UI and are not a canvas export. Installed 040653 passed one fresh 65,084-byte, 1,492 by 712 renderer capture with nonzero RGB and visual acceptance of the disposable PCB plus app UI, then original exit/release and byte-exact closed fixture. - For disposable project/PCB opening and bounded object observations on 3.2.209, read [the209 opening workflow](current-pcb209-opening.md), discover `pcb209-opening` and use the separate `easyeda_control_pcb209_opening` owner. ## Legacy design navigation

- For legacy typed design/library edits, inspect `easyeda_control_runtime`. That workflow requires `launch-contained`, a retained Windows Job and authenticated process proof. The current `project_symbol_metadata` route instead uses its separate ordinary-launch workflow above. An ordinary PID or a newly connected renderer supplies neither workflow's retained ownership.
- From Start Page, establish authenticated status and use runtime `open-existing` for an exact saved PCB or schematic-page target; see the connection reference. An unfinished design or library journal uses its own `open-target` recovery instead.
- When sibling editor tabs are already open, use supported library `document.open`, not exclusive Start Page `open-existing`. Successful navigation can precede editor readiness; observe fresh exact context without repeating the open.
- Before navigation or Save/reopen, read [navigation side effects](native-ui.md#navigation-preference-side-effects). PCB/footprint tab changes can write global preferences and prune local backups. A native tree click is not a workaround; do not change settings to pass admission.
- If the user started EasyEDA separately, use `easyeda_control_native_ui` discover, retain its observed-unowned `appBinding`, then inspect windows. A confirmed normal-close may request closure before a contained launch. Read [native-ui.md](native-ui.md); do not choose Save or Discard for unrelated work.
- Before legacy bridge design calls, require responsive authenticated `easyeda_control_status`, then `easyeda_control_context` with the actual project path/UUID, document UUID/type and tab. Type 15 is a 3D preview, not PCB. The restricted current metadata route does not expose legacy context; its original-owner workflow performs its own context checks.
- The reviewed tuple is connected-read-admitted. A `validation-required` mismatch permits only the bounded public validation workflow; never refresh pins merely to make it pass.
