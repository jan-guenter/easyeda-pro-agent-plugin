The separate `easyeda_control_current_schematic_relevance_display_write` tool
accepts one generated seven-record explicit-Relevance schematic. It prepares
one bounded Text display patch, one Modify and one Save, then verifies a separate
fresh saved-reader generation. Ordinary projects, other fixture profiles and
inverses remain unavailable. Connected writer validation is unclaimed.

```json
{"request":{"action":"schematic209-relevance-display-write","query":{"includeSchemas":true}}}
```

The public tool is registered only in the current public-utilities profile.
Registration and matching schemas do not enable an incomplete native route.
The original Modify, Save and drain composition must exist before allocation.
At this source checkpoint those completion wrappers remain incomplete. The
writer-specific pre-opening registration has its own original 32-request Main
continuation and cannot reuse a Saved intent. Report the original refusal;
do not substitute an SDK call, a callback table or another owner.

## Prepare the original source

Use the [generated fixture importer](managed-fixture-import.md) and its distinct
explicit-Relevance profile. Requalify its original closed data through
`easyeda_control_fixture_data` in a fresh facade, then finish that coordinator's
original file/watch leases, proof helper and record publication. Query
`closed-generated-fixture-data` for exact current arguments.

Writer `prepare` takes that original `fixtureOperationId`, a new
`sch209-relevance-display-*` operation ID and a strict display patch. The
seven-record source is consumed synchronously before checkpoint work. Other
fixture families refuse before staging their token. No supplied path, UUID,
JSON checkpoint, journal or historical process can replace that source.

Validate requests with offline `schematic209-relevance-display-write-validate`.
`execute` requires every literal confirmation in its schema. These fields
record scope; actual source, native owner and receipt checks still authorize
each dispatch. Missing original composition refuses before native allocation.

## Original execution and cleanup

The coordinator retains its original execution Promise while `inspect` remains
available. Each action result has a separate readonly `diagnostic` with the
original stage and first bounded uppercase error code. Inspect after a background
refusal to retain that cause without exposing private paths or stack/cause data.
Codes require the same original server-issued Error identity. An unknown SDK or
native error remains unclassified even if its message resembles a source code.
The diagnostic supplies no execution or saved-state proof.
The writer journal records the original startup cancellation,
library-refresh exclusion, Modify and once-only Save intents. Save observation,
local production and the original Main/upload drain run together. Genuine
completion must preserve the Relevance ATTR and every peer. Root zIndex
normalization is an explicit in-memory bookkeeping effect.

After original normal close, root exit, empty Job and complete closed SQL/source
capture, the writer releases its own helper. Only that genuine closed lifecycle
can prepare the separate saved reader. The reader owns fresh cache backup and
invalidation, cold loading, registration, project/page opening, scene comparison,
normal close, complete closed SQL/raw-history comparison and its helper release.
Neither an SDK result nor scene data alone proves saved state.

On failure, keep the original controller and operation. Do not replay Modify,
Save, navigation or execute. `abort` addresses only its retained original Job.
An unknown abort acknowledgement permits independent original exit observation,
never another abort. File-handle closure, process termination and helper release
are separate proofs. A poisoned file-capture release stays unresolved even if
native cleanup succeeds.

Use `settle-publication` for retained original publication failures. The bounded
`observe-termination` and `release` actions join original cleanup. After all
resources close, a separate immutable abandonment receipt may clear historical
admission while saved/reopened remain false. That receipt supplies no retry,
inverse, owner transfer or acceptance of the failed fixture.

Require completed status with saved, reopened, complete SQL and peer preservation
true, both original helpers released and no pending publication. Then use the
normal [retirement/update workflow](connection-and-context.md#cooperative-retirement-and-update-handoff).
