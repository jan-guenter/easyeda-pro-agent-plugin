# Generated schematic opening and reads

Use this development route only when the loaded controller exposes
`generated-schematic-opening` and its validation query. It consumes the real
SCH/SCH_PAGE fixture produced by `schematic-text-wire-bus`; it accepts no caller
path, project/page ID, source, primitive ID or JavaScript. It opens no existing
user project and provides no edit, Save, connectivity or persistence authority.

Complete the import's original normal cleanup and closed qualification. Release
its destination and owner, then call `stage-schematic-for-fresh-opening` with
the original base import ID and `confirmStageClosedFixture:true`, before
ordinary helper release. Finish that launch's termination record and helper
release. Keep the same facade. Staging retains only opaque qualified data;
it transfers no runtime, process, Job, HMAC session or native watch.

Launch a new ordinary application through `easyeda_control_launch`. Obtain its
actual authenticated fingerprint and query the exact generated-schematic schema.
Use a unique `sch209-generated-...` operation ID. The existing
`easyeda_control_pcb209_opening` tool takes this wrapper:

```typescript
const argumentsValue = {
  request: {
    action: "generated-schematic",
    request: {
      action: "open-generated-schematic",
      operationId: "sch209-generated-example",
      confirmGeneratedDisposableFixture: true,
      acceptRecentPathRegistration: true,
      acceptNormalOpenEffects: true
    },
    expectedFingerprint: observedFingerprint
  }
};
```

Here `observedFingerprint` is the complete actual status fingerprint object.
The route binds a different original ordinary runtime and launch. Registration,
project opening and page opening each run once from the original token, with
checkpoint and full source guards. One recent-path registry row may change.
Ordinary opening and closure may also persist shared state or the generated
file. Native acknowledgment and independent page readiness are separate.
Never repeat navigation after failure, a partial return or immediate readiness
refusal. Retain the exact attempted prefix and continue original cleanup.

After page-open acknowledgment, the separate `observe-text-wire-bus` action,
with the same operation ID, `confirmGeneratedReadOnly:true` and complete
fingerprint, consumes one passive reader batch. It independently checks the
same window, page and schematic parent, and derives every target and primitive
identity from the qualified source. It offers no selection change, electrical
compiler, topology repair or Save. Missing/stale state refuses the whole batch.

Inspect in a separate call after the open or read call settles. The result
built inside an authenticated scope may precede issuance of its cleanup nonce.
Use only the later original technical nonce and operation ID for
`request-cleanup-close`, `observe-cleanup-termination` and `finish-cleanup`.
Close requires `confirmNormalClose:true` and `acceptUnknownFileEffects:true`.
Leave Save/Discard prompts unanswered. `settle-records` and
`settle-cleanup-records` publish retained local bytes without repeating a
native call. Then `release-owner` requires
`confirmReleaseGeneratedSchematicOwner:true`.

Only after that owner release may the original ordinary launch publish its
termination record and release its helper. An attempted or released data token
cannot be retried, reconstructed from JSON or moved to another facade. A new
controller or plugin update requires the original helper release and facade
retirement first; use the maintained manager rather than restarting Codex.
